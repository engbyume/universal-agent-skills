# Conditional platform and lifecycle security checks

Use this reference with the 70 general checks in application-security-checks.md. These 19 additional checks cover platforms and operational practices that apply only to some products. Apply the sections that match the architecture, data, release path, and threat model. Record a reason when a section is not applicable. For every applicable check, state the control and how it will be verified. This is not a certification checklist.

| # | Check | Security review guidance |
|---|---|---|
| 71 | Software bill of materials (SBOM) | For each distributed release, generate a machine-readable SBOM that identifies direct and transitive components, versions, and dependency relationships. Include build and runtime components when the format and pipeline support it; record unknown or unresolved components. Verify the SBOM against the actual release artifact. See [NTIA minimum SBOM elements](https://www.ntia.gov/report/2021/minimum-elements-software-bill-materials-sbom). |
| 72 | Build provenance and artifact integrity | For released software, record which source revision, workflow, builder, and parameters produced the artifact. Sign or attest to the artifact and verify its origin and integrity before deployment or distribution. Reject artifacts from untrusted or unexpected build paths. See [SLSA v1.2](https://slsa.dev/spec/v1.2/) and [NIST SSDF 1.1](https://csrc.nist.gov/pubs/sp/800/218/final). |
| 73 | API inventory and retirement | If the product exposes APIs, inventory hosts, protocols, versions, environments, owners, authentication, and data handled. Compare the inventory with deployed routes, gateways, and DNS. Retire obsolete versions and restrict previews, test endpoints, and old deployments; any version that remains reachable must retain appropriate controls. See [OWASP API9:2023](https://api-security.owasp.org/editions/2023/en/0xa9-improper-inventory-management/). |
| 74 | Unsafe consumption of external APIs | Treat third-party API responses as untrusted. Validate schema, size, content type, and values; set timeouts; constrain redirects and outbound destinations; and send only necessary data to the provider. Verify malformed, oversized, delayed, and redirected responses fail safely. See [OWASP API10:2023](https://api-security.owasp.org/editions/2023/en/0xaa-unsafe-consumption-of-apis/). |
| 75 | Expensive or complex API requests | For GraphQL, batch APIs, search, AI, and other costly endpoints, limit both request frequency and work per request. Consider query depth or cost, batch size, page size, concurrency, per-user or per-tenant quotas, and provider spend alerts. Test deeply nested, oversized, batched, concurrent, and repeated requests. See [OWASP API4:2023](https://api-security.owasp.org/editions/2023/en/0xa4-unrestricted-resource-consumption/) and the [OWASP GraphQL Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/GraphQL_Cheat_Sheet.html). |
| 76 | Native mobile storage and backups | For native or hybrid apps, use platform secure-storage APIs for credentials and keys. Review app files, local databases, caches, backups, keyboard data, clipboard, and logs for sensitive content. Apply encryption and backup exclusions according to risk and platform behavior, then inspect an actual app backup or device state. See [OWASP MASVS storage controls](https://mas.owasp.org/MASVS/). |
| 77 | Mobile links and inter-app boundaries | For mobile apps, review deep and universal links, custom URL schemes, Android intents and exported components, inter-process communication, shared app groups, and WebView bridges. Validate caller, origin, destination, and authorization at each boundary. Test crafted links, messages, and intents. See [OWASP MASVS platform controls](https://mas.owasp.org/MASVS/09-MASVS-PLATFORM/). |
| 78 | Mobile permissions and sensitive presentation | Request only needed operating-system permissions and handle denial or revocation safely. Check notifications, widgets, app-switcher previews, screenshots, screen recording, and background behavior for sensitive-data exposure. Test lock-screen and background states on supported platforms. See [OWASP MASVS privacy controls](https://mas.owasp.org/MASVS/12-MASVS-PRIVACY/). |
| 79 | Multiplayer game authority and economy | For networked games, keep match results, inventory, currency, cooldowns, progression, and rewards under trusted server or service control. Validate player actions and make high-impact rewards idempotent or replay-resistant. Treat anti-cheat as defense in depth, not as the authority for game state. Test tampered clients and replayed actions. See [Unreal networking guidance](https://dev.epicgames.com/documentation/unreal-engine/networking-overview-for-unreal-engine) as an architecture example. |
| 80 | AI model and data provenance | If the product trains, fine-tunes, downloads, or serves models, record model and dataset origin, source authorization, version, integrity, and approved deployment path. Treat training, fine-tuning, and embedding data as inputs that can be poisoned. Review model formats for executable behavior before loading them. See [NIST SP 800-218A](https://csrc.nist.gov/pubs/sp/800/218/a/final) and [OWASP LLM04](https://genai.owasp.org/llmrisk/llm042025-data-and-model-poisoning/). |
| 81 | Retrieval access control and deletion | For RAG or vector search, apply the initiating user's and tenant's permissions before retrieved content enters a prompt. Test revoked access, deleted documents, stale indexes, and shared caches for cross-user disclosure. Confirm deletion and permission changes propagate to derived indexes and caches. See [OWASP LLM08](https://genai.owasp.org/llmrisk/llm082025-vector-and-embedding-weaknesses/). |
| 82 | Sensitive-data lifecycle | For personal or sensitive data, document purpose, access, sharing, retention, and deletion across primary stores, replicas, indexes, analytics, exports, backups, and subprocessors. State backup-retention limits accurately. Test the actual deletion or retention workflow across each applicable store. Use the [NIST Privacy Framework](https://www.nist.gov/privacy-framework) as a risk-management reference, not as a statement of legal obligations. |
| 83 | Incident response readiness | For released or production software, assign response ownership and maintain a runbook for detection, containment, credential revocation, recovery, evidence preservation, and communications. Exercise a realistic incident and update the runbook from the results. See [NIST SP 800-61 Rev. 3](https://csrc.nist.gov/pubs/sp/800/61/r3/final). |
| 84 | Vulnerability report intake | For distributed or internet-facing software, publish an appropriate security contact or vulnerability-reporting path. Assign triage ownership, track reports through remediation, and coordinate disclosure with affected parties. Keep legal notification decisions with qualified owners. See [NIST SP 800-216](https://csrc.nist.gov/pubs/sp/800/216/final) as a federal guidance model, not a universal legal requirement. |
| 85 | Backup separation and restore integrity | For critical persistent data, keep recovery copies protected from routine production identities. Consider offline or immutable copies when the threat model supports them. Test backup integrity and restore access controls, including tenant isolation. See [CISA ransomware guidance](https://www.cisa.gov/stopransomware/ransomware-guide). |
| 86 | Cloud workload identity | Where supported, use workload identity or federation with short-lived credentials instead of long-lived cloud keys. Restrict trust policies to expected issuers, subjects, and audiences. Inventory and remove unused identities. See [AWS IAM best practices](https://docs.aws.amazon.com/IAM/latest/UserGuide/best-practices.html), [Google Cloud workload identity guidance](https://docs.cloud.google.com/iam/docs/best-practices-for-using-workload-identity-federation), and the [Azure Security Benchmark identity controls](https://learn.microsoft.com/en-us/security/benchmark/azure/security-controls-v3-identity-management). |
| 87 | Temporary privileged access | For sensitive production administration, review standing administrator roles, break-glass accounts, approval requirements, session duration, and audit trails. Use time-bounded elevation where the provider and operating model support it. Verify expired elevation no longer grants access. |
| 88 | Phishing-resistant authentication and downgrade paths | For privileged or high-impact accounts, consider phishing-resistant authenticators such as correctly implemented WebAuthn or passkeys. Test registration, account binding, removal, recovery, and fallback so a weaker path does not silently bypass the intended assurance. Choose the requirement through threat and usability assessment; do not impose one authenticator type on every user. See [NIST SP 800-63B-4](https://pages.nist.gov/800-63-4/sp800-63b.html) and the [OWASP Passkey Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Passkey_Security_Cheat_Sheet.html). |
| 89 | Memory safety for native code | When the product uses memory-unsafe languages, native extensions, or complex parsers exposed to untrusted input, review unsafe code and compiler hardening. Use fuzzing or sanitizers for high-risk parsers where supported, and consider memory-safe components when practical. This is a risk-based control, not a blanket language mandate. See [CISA Secure by Design guidance](https://www.cisa.gov/sites/default/files/2023-10/SecureByDesign_508c.pdf). |

## Standard status

NIST SP 800-218 version 1.1 is final. SP 800-218 Revision 1 / version 1.2 is an initial public draft in this research snapshot; do not present draft recommendations as final requirements. NIST SP 800-218A is a final AI-focused profile intended to be used with SP 800-218 version 1.1. Recheck current versions when applying these standards.

Research source snapshot: 2026-10-09.
