# Application security checks for implementation work

This reference adds a security pass to implementation work for websites, apps, and games. It does not replace a threat model, project security review, or security testing. The initial list contained 16 checks despite being introduced as 15. Three later additions supplied 18 checks each, for 70 checks total. Apply checks that match the architecture and risk. Some checks apply only when the product uses the related feature: MFA, AI, CI/CD, dependencies, databases or cloud services, audit logs and monitoring, backups, internal dashboards, browser headers and cookies, sensitive data needing encryption, JWTs, uploads, outbound URL fetching, webhooks, payments, multiple deployment environments, multi-tenancy, OAuth, or native deserialization and process execution.

## Before building

Use the active `security-review` skill. Identify sensitive data and secret paths, trust boundaries, authentication, authorization, sessions, browser origins, password recovery, uploads, file paths, outbound URL fetching, API and webhook endpoints, payments, database roles, cloud configuration, deployment environments, source maps, package sources, audit and monitoring needs, backups, encryption boundaries, tenant boundaries, code review, object-property binding, process execution, deserialization, OAuth flows, and AI prompts and tools. Turn applicable checks into concrete controls and tests before implementation. Do not treat a missing feature as a finding without considering the product, threat model, and applicable policy.

| # | Check | Security review guidance |
|---|---|---|
| 1 | No multi-factor authentication | Assess whether MFA or step-up authentication is needed for administrators, sensitive data, account recovery, or high-impact actions. Do not treat the absence of MFA as a universal failure for every product or account. |
| 2 | Account enumeration | Review sign-up, login, password reset, recovery, and invite flows for differences in response content or timing that reveal whether an account exists. Use consistent responses and suitable abuse controls. |
| 3 | Business logic abuse | Test whether users can skip or reorder workflow steps, change prices or permissions in client requests, exceed quotas, or reuse one-time benefits. Enforce business invariants on the server. |
| 4 | Race conditions | Identify check-then-act operations such as payments, booking, coupon redemption, inventory, and account changes. Use atomic operations or idempotency where needed, then test concurrent requests and the final state. |
| 5 | Webhook replay | After a webhook's authenticity is verified, reject stale or repeated events using timestamps or event IDs when available. Make side effects idempotent and test duplicate and out-of-order delivery. See the webhook-signature check below for authenticity. |
| 6 | Insecure CI/CD | Review workflow permissions, secret access, deployment approvals, branch protections, artifact handling, and isolation between trusted code and untrusted contributions. Limit each workflow to the access it needs. |
| 7 | Untrusted build actions | Review third-party actions and reusable workflows before use. Pin actions to a full commit SHA where supported, restrict allowed actions, and do not execute untrusted pull-request code with privileged tokens or secrets. |
| 8 | Unpinned build dependencies | Use lockfiles and integrity checks. Pin build actions and other mutable inputs where practical. Do not rely on floating references for reproducible builds. Review known vulnerability findings under the vulnerable-dependency check below. |
| 9 | Checks fail open | Verify that authentication, authorization, validation, signature checks, security gates, and release checks do not silently allow a protected action after an error, timeout, or unknown result. Define safe fallback behavior for availability separately. |
| 10 | Missing timeouts | Set bounded timeouts, retry limits, and cancellation for network calls, database operations, webhooks, and AI services. Check that failures do not leave duplicate or partial high-impact actions. |
| 11 | Sensitive information leak | Inspect API and other responses, logs, analytics, crash reports, error messages, URLs, cached pages, and support/debug views for credentials, tokens, personal data, or internal details. Select response fields server-side and return only data the authorized caller needs; validate response schemas instead of relying on client or UI filtering. Redact or remove unnecessary data. |
| 12 | Invalid AI outputs | If the product uses AI, validate structured output against a schema, encode content for its destination, and treat model output as untrusted input. Do not pass it directly to shell, SQL, HTML, permissions, or business-rule decisions. |
| 13 | Excessive AI permissions | If the product uses AI tools or agents, minimize the functions, data, and autonomy available to the model. Remove unused tools and capabilities; keep high-impact operations behind explicit controls. See the separate check below for authorization in the initiating user's context. |
| 14 | Sensitive browser storage | Do not store session tokens, refresh tokens, credentials, or sensitive personal data in `localStorage` or `sessionStorage`. Choose a session design that fits the architecture, such as secure `HttpOnly` cookies or a backend-for-frontend, and test XSS and CSRF risks. |
| 15 | Open redirects | Do not redirect to an arbitrary user-supplied URL. Prefer local paths or server-side destination IDs. If external destinations are needed, parse and validate them against an explicit allowlist. |
| 16 | Unsecured endpoints | Inventory public, authenticated, administrative, debug, and webhook endpoints. Verify authentication and object-level authorization where required, validation, rate limits, method restrictions, transport protection, and safe error handling. Public-by-design endpoints still need abuse controls. For WebSocket, SSE, or managed realtime subscriptions, authenticate the connection and authorize each channel, topic, event, and tenant on the server. Validate browser origins, bound and validate messages, rate-limit clients, and expire or reauthorize connections after credential or permission changes. Test cross-user and cross-tenant subscription, publish, and stale-session cases. For Supabase Realtime, use private channels with scoped RLS policies. See the [OWASP WebSocket Security Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/WebSocket_Security_Cheat_Sheet.html), [Supabase Realtime Authorization](https://supabase.com/docs/guides/realtime/authorization), and [AWS AppSync realtime authorization](https://docs.aws.amazon.com/appsync/latest/devguide/aws-appsync-real-time-data.html). |
| 17 | Exposed database credentials | Keep database connection strings and passwords on trusted server or service boundaries. Check source, configuration, container images, build artifacts, and runtime responses for exposed credentials. Use scoped secret storage and rotate credentials found in an exposed location. |
| 18 | Publicly served `.env` files | Verify production web servers and static hosting do not serve `.env`, `.env.*`, backup, or local configuration files. Keep real secrets outside public asset roots. A sample file is safe only when it contains no real secret. |
| 19 | Hardcoded secrets | Scan application source and configuration for embedded passwords, private keys, tokens, and secret values. Load secrets from an approved runtime secret store. If a secret is exposed, revoke or rotate it, remove exposed copies from active source and deployment artifacts, and verify the replacement is loaded. Removing a current copy does not revoke an exposed value. |
| 20 | Weak authentication | Review sign-in, account recovery, session handling, throttling, and credential storage against the product's risk. Use a maintained authentication system where practical. If the application stores passwords, use a vetted adaptive password hash with a unique salt per password, preferring Argon2id where available. Never store plaintext or reversibly encrypted passwords, or use a fast general-purpose hash. Require MFA or step-up checks for privileged or high-impact flows when the threat model calls for them. |
| 21 | Missing authorization checks | Check every protected operation at the server or trusted service boundary. Verify the caller may perform the requested action on the specific resource. Hiding a control or route in the interface is not authorization. |
| 22 | Cross-user access | Check user-owned records and shared-resource flows so one user cannot view or change another user's private data through lists, search, exports, background jobs, or caches. Preserve explicit sharing rules. See the API-specific IDOR/BOLA check below for object-ID manipulation and the tenant-isolation check for multi-tenant boundaries. |
| 23 | Open database permissions | Check for publicly reachable database ports, anonymous access, unsafe default grants, and exposed management interfaces. Restrict network access to trusted services. Public data access must be deliberate and limited. See the separate database least-privilege check below for application-role grants. |
| 24 | Cloud and hosting misconfiguration | Review provider IAM, storage visibility, network rules, service identities, secret access, public management surfaces, and web server indexing settings. Disable directory listing or autoindex for locations that are not intended to be browsed, unless public listing is an explicit product feature. Verify deployed settings, not only source templates. See the [OWASP WSTG v4.2 review of unreferenced files and directory indexing](https://wstg.org/v4.2/4-Web_Application_Security_Testing/02-Configuration_and_Deployment_Management_Testing/04-Review_Old_Backup_and_Unreferenced_Files_for_Sensitive_Information/), checked 2026-10-12. |
| 25 | Unprotected admin routes | Identify administrative pages and API operations. Require server-side authentication and role checks, deny access by default, and add MFA or step-up authentication, rate controls, and audit logging where risk warrants them. |
| 26 | Exposed production debug tools | Disable development consoles, profilers, test routes, diagnostics, sample accounts, and debug endpoints in production. If a support tool must remain, protect it with strong access controls and restrict its network exposure. |
| 27 | Secrets in logs | Inspect application, proxy, CI/CD, analytics, and crash logs for passwords, tokens, cookies, authorization headers, database credentials, and sensitive request bodies. Redact before storage and restrict log access. |
| 28 | Verbose production errors | Return safe client errors without stack traces, SQL text, file paths, secrets, or internal configuration. Keep only necessary diagnostic detail in access-controlled logs, with sensitive values redacted. |
| 29 | Secrets in Git | Scan tracked files and repository history for credentials and private keys. Prevent new secrets with suitable pre-commit or CI checks. If a secret reached Git, revoke or rotate it; deleting the current line does not make the exposed value safe. |
| 30 | Secrets in JavaScript | Inspect browser and mobile client bundles, app packages, source maps, and delivered configuration for server credentials or private keys. Keep secrets on the server. Expose only provider-designated publishable or anonymous client keys, never secret, service-role, or admin keys. A public key is not authorization; enforce access at trusted service or database boundaries and apply provider-supported key restrictions. |
| 31 | Client-only security | Assume users can modify browser code, requests, and stored state. Enforce authorization, validation, quotas, and important business rules in trusted services or the database, then test direct requests that bypass the interface. |
| 32 | Input validation | Validate untrusted input at each server-side trust boundary. Check types, allowed fields, formats, ranges, lengths, nesting, and request size against the operation's schema. Keep validation separate from authorization and output encoding. |
| 33 | SQL injection (when using SQL) | Use parameterized queries or safe database APIs for values. Allowlist identifiers or sort choices that cannot be parameterized. Do not build SQL by concatenating untrusted input. |
| 34 | NoSQL injection (when using NoSQL) | Build typed database filters from validated fields and allowed operators. Do not accept raw client query objects or operator expressions as database queries. Test unexpected object types and operator-shaped input. |
| 35 | Cross-site scripting (XSS) | Render user-controlled text as text with the framework's escaping. Avoid unsafe DOM and HTML sinks. If users may submit rich HTML, sanitize it with a maintained allowlist sanitizer at the ingestion boundary before persisting it as markup. Treat stored content as untrusted during later rendering, encode it for the output context, and re-sanitize after any transformation that changes markup. Do not sanitize plain text solely to store it. Treat Content Security Policy as defense in depth, not a substitute for safe rendering. See the [OWASP XSS Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Cross_Site_Scripting_Prevention_Cheat_Sheet), reviewed 2026-10-12. |
| 36 | Cross-site request forgery (CSRF) | For browser requests authenticated by automatically sent cookies, use the framework's CSRF defenses or validated tokens and origin checks for state-changing operations. Do not mutate state on GET requests. Choose protections that fit the authentication method and test the sensitive flows. |
| 37 | Insecure file uploads | Allowlist required types and sizes, inspect content rather than trusting the filename or client MIME type, generate server-side names, and store files outside executable web roots. Enforce authorization and CSRF protections, and scan or sandbox risky formats when appropriate. |
| 38 | Path traversal | Do not use an untrusted path directly for file access. Prefer opaque file IDs mapped to authorized records. If paths are required, canonicalize before checking, confine resolved paths to an approved root, and test encoded separators and alternate path forms. |
| 39 | Server-side request forgery (SSRF) | If the server fetches user-selected URLs, allowlist destinations where possible. Restrict schemes, hosts, resolved IP ranges, redirects, and ports; block loopback, private, link-local, and cloud metadata destinations. Add outbound network controls, size limits, and timeouts. |
| 40 | Broken password reset | Use generic responses for known and unknown accounts. Generate high-entropy, single-use, expiring reset tokens, store them safely, rate-limit attempts, and change the account only after valid proof. Keep reset links on trusted HTTPS origins and prevent token leakage through referrers or logs. |
| 41 | Weak session management | Use unpredictable session identifiers and secure transport. Rotate sessions after login and privilege changes, invalidate them on logout and relevant credential changes, and enforce idle or absolute expiry on the server. Choose cookie protections and revocation behavior for the application. |
| 42 | JWT secrets and validation | If JWTs are used, keep signing keys secret and server-side. Use approved algorithms and keys, validate issuer, audience, expiry, and other required claims, reject invalid or unexpected key identifiers, and plan key rotation and revocation. Do not assume a JWT is encrypted. |
| 43 | Permissive CORS | If cross-origin access is needed, allow only intended origins, methods, and headers. Do not reflect arbitrary origins or combine credentialed requests with a wildcard origin. A wildcard may be valid for intentionally public, unauthenticated resources; CORS does not replace server authorization. |
| 44 | Missing rate limits | Apply server-side limits to relevant accounts, clients, actions, and resource costs, including login, sign-up, reset, uploads, search, expensive API operations, and value-dispensing flows. Choose limits that resist abuse without creating easy account lockout or denial-of-service paths. For login, sign-up, recovery, and other high-risk flows, layer risk-based bot or automation detection or challenges with rate limits. Do not rely on CAPTCHA or browser-only checks alone, and consider accessibility and false positives. |
| 45 | Exposed deployment environments | Inventory production, staging, development, preview, and test deployments. Restrict non-public environments, remove production data and secrets from lower-trust environments, and protect their APIs, logs, admin tools, and test accounts. |
| 46 | Default credentials | Remove or replace vendor, installer, sample, and test credentials before deployment. Require unique credentials or secure provisioning for each environment, and fail release checks when known defaults remain enabled. |
| 47 | Unsigned webhooks | Verify provider signatures over the exact request body using the documented method and signing key. Reject missing or invalid signatures and rotate signing keys safely. If a provider has no signature mechanism, use its documented authenticated verification method; do not trust source IP alone. See the replay check above for freshness and duplicate handling. |
| 48 | Frontend-only payment checks | Treat browser prices, discounts, payment status, and success redirects as untrusted. Calculate amounts and create payment sessions on the server. Confirm final state through the payment provider's verified server response or signed webhook, and make fulfillment idempotent. |
| 49 | Insecure direct object reference (IDOR) and broken object-level authorization (BOLA) | For API endpoints that accept object IDs, alter path, query, and body IDs and test the requested read, update, delete, or export action. Authorize the exact object and action on the server, including nested and batched requests; unguessable IDs are not authorization. |
| 50 | APIs that accept user input | Treat path, query, headers, body, content type, and uploaded data as untrusted at every API boundary. Apply schema and size limits, authorization, safe parsing, and resource controls. Test the API directly, including requests that bypass the UI and data returned by external services. |
| 51 | Exposed logs | Check whether log files, dashboards, search endpoints, exports, and storage buckets are public or available to roles that do not need them. Require access controls, protect exports and backups, and apply appropriate retention and redaction. |
| 52 | Exposed source maps | Review production source maps and bundles for secrets, sensitive comments, internal endpoints, and unintended source disclosure. Publish maps only when intended or restrict access through the build and error-reporting setup. Source maps are not automatically a vulnerability. |
| 53 | Vulnerable dependencies | Inventory direct and transitive dependencies, runtimes, and platform components. Check supported versions and known vulnerability advisories; update or apply a documented mitigation based on exposure and impact. Keep the review tied to the actual lockfile and build. |
| 54 | Malicious packages | Verify package names, registries, maintainers, provenance or signatures where available, and install scripts before adding dependencies. Check for typosquatting, unexpected ownership changes, and suspicious behavior. Restrict package sources and build permissions to what the project needs. |
| 55 | Prompt injection | If AI features process user or retrieved content, treat that content as untrusted data that may contain direct or indirect instructions. Separate it from trusted policy, constrain model outputs and tool choices, and enforce security decisions in code. Do not rely on prompt wording alone as an authorization boundary. |
| 56 | Unpermissioned AI access | If AI can read data or call tools, authorize each action in the initiating user's and tenant's context. Do not let a shared service identity grant the model access to data or actions the user lacks. Deny calls when identity or permission checks are missing, and require confirmation where appropriate. |
| 57 | Excessive database permissions | Give each database service identity only the operations, tables, and rows it needs. Avoid owner, administrator, or broad write roles for routine application work. When client or data API access relies on row-level security (RLS) or equivalent row/document policies, explicitly enable policies on every exposed user-scoped table, define allowed operations, and test both allowed and denied access for anonymous, authenticated, and service roles. Check grants separately, because policies may not revoke grants. Keep roles that bypass policies server-side. |
| 58 | Missing audit logs | Record security-critical actions such as authentication and recovery events, privilege changes, administrative actions, sensitive data exports, payment state changes, and policy updates. Include attributable actor, action, target, result, and time while excluding secrets and unnecessary personal data. Protect audit records from unauthorized changes or deletion. |
| 59 | Missing security monitoring | For production or other risk-bearing deployments, decide which security events need alerting and who responds. Monitor relevant authentication failures, privilege changes, unusual data access, service errors, and security-control failures. Test that alerts reach an owned response path; scale monitoring to the threat and service. |
| 60 | Missing backup and restore | For persistent data or configuration, define recovery objectives and retention. Protect and encrypt backups, restrict access, separate them from the primary service, and test restores on a schedule. Verify restored data and access controls, including tenant separation where applicable. |
| 61 | Exposed internal dashboards | Inventory monitoring, analytics, support, and operations dashboards. Restrict them to authorized users and networks, apply least-privilege roles, and prevent public indexing or unauthenticated access to operational and customer data. |
| 62 | Missing security headers | For web responses, select appropriate headers for the product, such as HSTS, Content-Security-Policy, frame restrictions, content-type protection, and Referrer-Policy. Verify them on relevant routes. For HTTPS-only sites, use HSTS only after confirming every covered host supports HTTPS. Avoid copying a policy that breaks intended platform behavior. Headers add defense in depth and do not replace secure code. |
| 63 | Insecure cookie settings | For cookies carrying sessions or sensitive state, review `Secure`, `HttpOnly`, and `SameSite` attributes, scope, lifetime, and HTTPS behavior. Choose settings for the actual cross-site flow and test login, logout, and session renewal. |
| 64 | Unencrypted data | Classify sensitive data and protect it in transit with current TLS and at rest with suitable storage encryption where required by risk or policy. Use HTTPS for browser and API traffic; redirect web requests from HTTP or reject plaintext HTTP at API boundaries. Verify production routes do not serve sensitive content over HTTP. Protect and separate keys, avoid custom cryptography, and minimize data that must be retained. |
| 65 | Poor tenant isolation | If the product is multi-tenant, define the tenant boundary across databases, caches, object storage, search, background jobs, analytics, exports, and backups. Derive tenant identity from an authorized server-side context, not an unchecked client value. Test that cross-tenant reads and writes fail. |
| 66 | Unreviewed code | Before release, require an appropriate review for production code, dependency, and security-configuration changes. Protect branches and required checks where the workflow supports them. Document exceptions and complete a follow-up review for emergency changes. |
| 67 | Mass assignment | When binding API input to internal objects, explicitly allow writable properties. Reject or ignore client attempts to set protected fields such as role, owner, tenant, price, or account status. Validate output properties separately from input authorization. |
| 68 | Command injection | Avoid invoking operating-system commands with user-controlled data. Prefer safe library APIs; if process execution is necessary, use structured argument APIs, strict allowlists, and least privilege. Do not build shell command strings from input. |
| 69 | Insecure deserialization | Do not deserialize untrusted input into native or polymorphic object types. Prefer simple data formats with strict schemas and size limits. Allowlist required types, keep parsing libraries current, and verify integrity when the format depends on a trusted producer. |
| 70 | Misconfigured OAuth | If OAuth 2.0 is used, validate exact redirect URIs, protect authorization responses with correctly bound `state` or PKCE as supported by the flow, use PKCE with authorization-code flows, especially for public clients, check issuer when multiple authorization servers are used, and scope and protect tokens. For OpenID Connect, validate ID tokens according to the flow, including signature, issuer, audience, expiry, and `nonce` when required. Review refresh and revocation behavior and test account-linking flows. |

## After building

Run the `security-review` checks and relevant tests for the changed code. Recheck every applicable item above, including workflows and third-party components when in scope. Use static analysis, secret and dependency scanning, database or cloud permission review, backup restore checks, browser security tests, monitoring and audit-log verification, and authorized local or staging security tests as appropriate. Keep dynamic testing within the project or target scope the user owns or has authorized. Fix confirmed findings and rerun the failing checks. Record unavailable or unrun checks explicitly. A clean checklist or automated scan is not proof that an application is secure.
